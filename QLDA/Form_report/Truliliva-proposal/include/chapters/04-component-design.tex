\section{Nguyên tắc phân rã}

Hệ thống được phân rã theo ranh giới triển khai và hợp đồng dữ liệu thực tế. Firmware,
simulator, Device Monitor, SmartWater Admin và worker .NET là các tiến trình độc lập;
HiveMQ và MySQL là hạ tầng ngoài tiến trình. Trạng thái dưới đây phản ánh source tĩnh,
không xác nhận các tiến trình đã cùng chạy trong một môi trường (E-FW-01--E-MQ-06).

\subsection{Đánh giá Simulator}

Simulator được phân loại ở mức \textit{Implemented}; payload phát sinh phù hợp với
contract telemetry hiện tại.

\begin{itemize}
    \item Simulator đã triển khai chức năng publish telemetry qua MQTT.
    \item Trường \texttt{MCU\_ID} được gửi trực tiếp dưới dạng chuỗi.
    \item Device Monitor chấp nhận \texttt{mcu\_id} là chuỗi không rỗng tối đa 50 ký tự.
    \item API SmartWater Admin áp dụng cùng giới hạn chuỗi cho \texttt{mcu\_id}.
\end{itemize}

Nguồn bằng chứng:

\begin{itemize}
    \item \texttt{SimulatorApp.cpp}
    \item \texttt{TelemetryRepository.php}
    \item \texttt{TelemetryController.php}
\end{itemize}
\section{Thiết kế nội bộ theo tiến trình}

\subsection{Firmware và simulator}

Firmware chính dùng \texttt{DeviceManager} làm điều phối vòng đời và
\texttt{MQTTManager} làm adapter broker. Adapter giữ \texttt{WiFiClientSecure},
\texttt{PubSubClient}, callback command, bộ đếm reconnect và các thao tác publish.
Simulator thu nhỏ cấu trúc này thành \texttt{SimulatorApp}, \texttt{WifiManager} và
\texttt{MqttManager}; lớp app quyết định chu kỳ/phayload, lớp MQTT chỉ kết nối và phát
(E-FW-02--E-FW-04, E-SIM-02--E-SIM-04).

\subsection{Device Monitor}

\path|public/index.php| là composition root và route table. \texttt{TelemetryService}
chuẩn hóa payload; \texttt{TelemetryRepository} cô lập SQL; \texttt{Database} tạo PDO
và DDL tương thích; \texttt{Responder}/\texttt{View} tách JSON và HTML. Trình duyệt là
MQTT consumer thực tế, vì PHP backend không chứa MQTT client (E-DM-02--E-DM-06).

\subsection{SmartWater Admin}

Luồng web chủ đạo là Route $\rightarrow$ Controller $\rightarrow$ Service
$\rightarrow$ Eloquent $\rightarrow$ MySQL $\rightarrow$ Blade. Telemetry ingest là
ngoại lệ: controller validate và tạo model trực tiếp; file
\path|app/Services/TelemetryService.php| không có implementation. Các module và giới
hạn chi tiết nằm tại Chương~\ref{chap:smartwater-admin} (E-ADM-04--E-ADM-06).

\subsection{Worker .NET}

\path|Program.cs| đăng ký options, repository, service và hosted worker.
\texttt{Worker} chỉ quản lý vòng đời; \texttt{MqttService} kết nối/subscription;
\texttt{DeviceService} giải mã DTO; \texttt{DeviceRepository} thực thi Dapper. Cấu
trúc lớp là \textit{Implemented}, nhưng tích hợp toàn hệ thống là
\textit{Partially Implemented} do hợp đồng legacy (E-MQ-01--E-MQ-05).

\section{Ranh giới nhất quán và giao dịch}

Device Monitor ghi từng message bằng một câu \texttt{INSERT}; không có transaction
phân tán giữa broker và database. Admin dùng transaction trong các nghiệp vụ hợp đồng,
gán/thay thiết bị, nhưng API telemetry chỉ tạo một bản ghi Eloquent. Worker ghi
\texttt{device\_data} rồi mới đọc/upsert \texttt{devices}; source không bao hai bước
trong một transaction. Cơ chế exactly-once, idempotency key và outbox đều
\textit{Not Found}. Do đó việc broker giao lại message có thể tạo bản ghi trùng; đây
là giới hạn thiết kế, không phải bằng chứng lỗi runtime.
